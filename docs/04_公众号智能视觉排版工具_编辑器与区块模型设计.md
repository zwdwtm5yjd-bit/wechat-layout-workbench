# 一、设计结论

本系统编辑器正式采用以下总体方案：

```text
React前端
+ Tiptap编辑器层
+ ProseMirror文档模型与事务系统
+ 自定义微信公众号区块扩展
+ JSON作为唯一权威内容源
+ 服务端微信HTML渲染器
+ 独立主题Token与品牌Token
+ 静态组件和SVG组件注册机制
```

核心原则：

1. 编辑器中的文章不是一段HTML，而是一棵受Schema约束的结构化文档树；
2. 数据库保存编辑器JSON，不以HTML作为主数据；
3. 微信HTML仅在预览、复制、同步和导出时生成；
4. 所有静态组件与SVG互动都必须注册为受控节点；
5. 用户不能在第一版执行任意HTML、CSS或JavaScript；
6. 主题与公众号品牌通过Token作用于文档，不直接污染正文内容；
7. 原文锁定通过事务拦截和内容指纹共同实现；
8. 撤销、重做、自动保存和版本快照统一围绕编辑事务设计；
9. 第一版单用户，不引入实时协同的运行复杂度；
10. 数据结构预留Yjs协同接口，后续多人编辑时无需推倒重做。

# 二、技术选型

# 2.1 推荐编辑器：Tiptap

Tiptap建立在ProseMirror之上，提供：

- Schema驱动的文档模型；
- Node、Mark和Extension扩展机制；
- JSON文档输出；
- HTML导入与导出；
- 命令系统；
- 事务系统；
- React集成；
- 自定义Node View；
- 服务端静态渲染；
- 后续协同编辑扩展能力。

选择Tiptap的原因不是其默认编辑器外观，而是：

> 它允许项目在ProseMirror稳定文档模型之上，较高效率地开发大量自定义公众号区块。

# 2.2 为什么不直接使用HTML编辑器

若直接把HTML作为编辑器核心，会产生：

- 结构识别困难；
- 主题替换困难；
- 组件升级困难；
- 微信兼容规则无法精确定位；
- 原文锁定难以实现；
- 撤销记录粒度混乱；
- 导入脏HTML后容易污染全文；
- SVG与静态组件无法统一；
- 历史版本差异难以比较。

因此，HTML只作为：

- 外部导入格式；
- 微信导出格式；
- 静态预览格式；
- 调试格式。

不得作为数据库唯一内容源。

# 2.3 为什么不首选Lexical

Lexical同样适合构建高性能富文本编辑器，但本项目更需要：

- 成熟的结构Schema；
- 大量区块扩展；
- HTML与JSON转换；
- 服务端静态渲染；
- 复杂Node View；
- 可控事务拦截；
- 微信导出规则。

综合开发成本与现成生态，首版选择Tiptap更稳妥。

# 2.4 Yjs使用策略

Yjs可用于未来：

- 多人实时协同；
- 多设备同步；
- 离线编辑；
- 冲突自动合并；
- 协同光标；
- 评论和批注。

第一版不启用实时协同，原因：

- 当前只有一个用户；
- 实时协同增加服务端和调试复杂度；
- 会影响版本、撤销和备份设计；
- 不是首版核心价值。

但文档ID、事务来源和区块ID应从第一版预留协同能力。

# 四、文档数据模型

# 4.1 文档根结构

数据库中的编辑器主数据使用JSON。

示例：

```json
{
  "schemaVersion": "1.0.0",
  "documentId": "doc_01JXYZ",
  "articleId": "article_01JXYZ",
  "accountId": "account_01",
  "themeId": "theme_inspection_modern",
  "themeVersion": "1.2.0",
  "brandVersion": "1.0.0",
  "content": {
    "type": "doc",
    "content": []
  },
  "meta": {
    "sourceType": "docx",
    "originalFileId": "file_01",
    "originalTextHash": "sha256:...",
    "textLocked": true,
    "createdAt": "2026-07-29T14:00:00+08:00",
    "updatedAt": "2026-07-29T14:20:00+08:00"
  }
}
```

# 4.2 文档根节点

ProseMirror根节点：

```json
{
  "type": "doc",
  "content": [
    {
      "type": "articleMeta"
    },
    {
      "type": "articleBody"
    },
    {
      "type": "articleFooter"
    }
  ]
}
```

建议文档逻辑上分为：

1. `articleMeta`：标题、作者、来源等非正文信息；
2. `articleBody`：公众号正文；
3. `articleFooter`：二维码、版权和固定文末。

微信正文复制时主要导出`articleBody`和允许导出的`articleFooter`。

# 六、基础节点Schema

# 6.1 文档节点

## `doc`

允许：

```text
articleMeta? articleBody articleFooter?
```

## `articleMeta`

包含：

- 主标题；
- 副标题；
- 作者；
- 来源；
- 原稿元信息。

该节点可不进入微信正文输出。

## `articleBody`

包含：

```text
block+
```

## `articleFooter`

包含：

- 固定署名；
- 版权声明；
- 二维码；
- 关注引导；
- 相关文章。

# 七、文本节点

# 7.1 主标题 `articleTitle`

属性：

```json
{
  "blockId": "blk_001",
  "semanticRole": "article_title",
  "sourceId": "src_001",
  "locked": true,
  "styleRef": "title.article.default",
  "customStyle": null
}
```

说明：

- 文档中只允许一个主标题；
- 默认不进入微信正文，可由用户选择作为首屏输出；
- 标题文字受原文锁定保护；
- 可应用封面或首屏样式。

# 7.2 副标题 `subtitle`

用途：

- 主标题补充；
- 栏目说明；
- 日期或主题信息。

# 7.3 标题 `heading`

统一节点，通过`level`区分：

```json
{
  "level": 1,
  "numbering": "一、",
  "semanticRole": "section_heading",
  "styleRef": "heading.level1.default"
}
```

支持：

- `level: 1`；
- `level: 2`；
- `level: 3`。

不得无限增加标题层级，公众号正文最多使用三级。

# 7.4 正文 `paragraph`

属性：

```json
{
  "blockId": "blk_011",
  "sourceId": "src_011",
  "semanticRole": "body",
  "locked": true,
  "styleRef": "paragraph.default",
  "customStyle": null,
  "indentMode": "none"
}
```

# 7.5 引用 `blockquote`

属性：

- 引用类型；
- 来源；
- 风格变体；
- 是否显示引号；
- 是否显示来源栏。

# 7.6 有序列表 `orderedList`

属性：

- 编号风格；
- 起始编号；
- 缩进级别；
- 是否转换为卡片；
- 原始编号文本。

党政、公文和法律内容必须保留原编号信息。

# 7.7 无序列表 `bulletList`

支持：

- 圆点；
- 方点；
- 对勾；
- 箭头；
- 品牌图标。

# 7.8 分割线 `divider`

属性：

- 变体；
- 宽度；
- 对齐；
- 图标；
- 上下间距；
- 兼容级别。

# 八、行内标记Mark

允许的Mark：

- `bold`；
- `italic`；
- `underline`；
- `strike`；
- `textColor`；
- `backgroundColor`；
- `link`；
- `inlineCode`；
- `highlight`；
- `textStyle`。

限制：

1. 禁止任意字体Mark直接写入文档；
2. 字体优先由主题和品牌控制；
3. 局部字体选择只允许系统白名单；
4. 不支持任意CSS字符串；
5. 链接需要安全校验；
6. 原文锁定不禁止Mark调整；
7. Mark变化不计入文字内容变化。

# 九、媒体节点

# 9.1 图片 `imageBlock`

属性：

```json
{
  "blockId": "blk_img_001",
  "resourceId": "res_img_001",
  "originalResourceId": "res_img_original_001",
  "alt": "",
  "caption": "",
  "widthMode": "full",
  "widthPercent": 100,
  "aspectRatio": "auto",
  "objectFit": "cover",
  "borderRadiusToken": "radius.md",
  "borderToken": null,
  "shadowToken": null,
  "watermarkId": null,
  "styleRef": "image.default",
  "compatibilityLevel": "safe"
}
```

图片节点不直接保存外部URL，而保存`resourceId`。

渲染时由资源服务生成：

- 编辑器地址；
- 预览地址；
- 微信导出地址；
- 静态降级地址。

# 9.2 图组 `imageGallery`

属性：

- 图片资源列表；
- 布局ID；
- 图片顺序；
- 比例；
- 间距；
- 是否互动；
- 降级布局；
- 图注策略。

# 9.3 GIF `gifBlock`

属性：

- 原GIF；
- 优化GIF；
- 静态首帧；
- 文件大小；
- 自动播放提示；
- 降级策略。

# 9.4 视频与音频

第一版只保留受控占位节点：

- `videoPlaceholder`；
- `audioPlaceholder`。

实际发布时优先通过微信后台原生能力插入，不自行生成复杂播放器。

# 十、结构节点

# 10.1 章节 `section`

章节是逻辑容器，不一定生成额外HTML。

结构：

```json
{
  "type": "section",
  "attrs": {
    "sectionId": "sec_01",
    "level": 1,
    "collapsedInOutline": false,
    "locked": false
  },
  "content": [
    {"type": "heading"},
    {"type": "paragraph"}
  ]
}
```

用途：

- 左侧目录；
- 章节拖动；
- 整章应用主题；
- 分章节快速排版；
- 章节折叠；
- 版本差异比较。

# 10.2 受控容器 `designContainer`

用于卡片、背景块和布局组合。

属性：

- 容器类型；
- 背景Token；
- 边框Token；
- 圆角Token；
- 内边距Token；
- 外边距Token；
- 允许的子节点类型；
- 兼容策略。

禁止容器无限嵌套。

建议最大嵌套深度：

```text
articleBody
→ section
→ designContainer
→ 基础内容节点
```

不允许超过三级可视容器，避免编辑复杂和微信HTML膨胀。

# 10.3 列布局 `columnLayout`

仅支持微信兼容范围内的固定结构：

- 两列；
- 三列；
- 左一右二；
- 左二右一；
- 图片文字组合。

不允许任意CSS Grid。

导出时转换为经过验证的安全结构。

# 十一、专业语义组件节点

专业组件不是一段固定HTML，而是：

```text

+ 内容槽位
+ 主题变体
+ 品牌Token
```

# 11.1 通用组件节点 `semanticCard`

属性：

```json
{
  "blockId": "blk_card_001",
  "componentId": "component_legal_focus",
  "componentVersion": "1.1.0",
  "semanticRole": "legal_issue",
  "variant": "line-left",
  "styleRef": "component.legal.focus",
```

在ProseMirror内部，正文Slot仍使用子节点，而不是把长文本放入属性字符串。


# 12.3 SVG内容限制

- 不保存任意用户脚本；
- 不允许远程JavaScript；
- 不允许未知外链；
- 动画和互动由系统模板生成；
- 专业模式只能调整白名单参数；
- 生成结果必须通过SVG清洗器；
- 必须有静态备用资源。

# 12.4 编辑器显示

Node View中显示：

- 实时互动预览；
- 互动类型标签；
- 兼容级别；
- 静态备用状态；
- 编辑按钮；
- 暂停动画按钮。

编辑器失焦时应暂停不必要动画，降低性能开销。

# 13.1 二维码 `qrCodeBlock`

属性：

# 十四、区块统一属性

每个Block级节点应具备统一基础属性：

```json
{
  "blockId": "blk_unique_id",
  "sourceId": "src_original_id",
  "semanticRole": "body",
  "locked": false,
  "hidden": false,
  "styleRef": "style.reference",
  "customStyle": null,
  "componentVersion": null,
  "compatibilityLevel": "safe",
  "createdAt": "2026-07-29T14:00:00+08:00",
  "updatedAt": "2026-07-29T14:20:00+08:00"
}
```

说明：

- `blockId`：编辑后的稳定节点ID；
- `sourceId`：对应原稿区块ID；
- `semanticRole`：内容语义；
- `locked`：是否锁定；
- `hidden`：预览时是否隐藏；
- `styleRef`：引用主题或组件样式；
- `customStyle`：用户局部覆盖；
- `componentVersion`：组件版本；

# 十九、原文锁定实现

# 19.1 锁定级别

## 全文锁定

禁止修改所有原始文字。

## 章节锁定

只锁定指定章节。

## 区块锁定

锁定单个区块。

# 19.2 事务拦截

ProseMirror所有变更通过Transaction进入。

系统在`filterTransaction`或等效事务拦截层检查：

- 是否修改锁定节点的文本；
- 是否删除锁定文本；
- 是否改变锁定文本顺序；
- 是否合并或拆分锁定段落；
- 是否修改编号原文。

允许：

- 修改Mark；
- 修改受控样式属性；
- 移动完整锁定区块；
- 更换组件外壳；
- 调整图片样式；
- 增加设计节点。

# 19.3 内容指纹

每个原文区块保存标准化文本哈希。

标准化处理：

- 统一换行；
- 不忽略标点；
- 不忽略数字；
- 不忽略空格差异，党政和法律模式下尤其严格。

每次：

- 快速排版后；
- 公众号切换后；
- 兼容修复后；
- 复制前；
- 同步前；

重新校验哈希。

# 19.4 变化报告

显示：

- 原文字数；
- 当前文字数；
- 新增字符；
- 删除字符；
- 修改字符；
- 顺序变化；
- 仅样式变化。

锁定状态下，正常结果应为：

```text
原文文字变化：0
视觉样式变化：若干
新增设计组件：若干
```

# 19.5 解锁流程

用户主动解锁时：

1. 显示风险说明；
2. 生成解锁前版本；
3. 选择全文或局部解锁；
4. 开始记录文字差异；
5. 复制前显示最终文字变化清单。

# 四十、技术风险与控制

| 风险 | 控制措施 |
|---|---|
| 自定义节点过多 | 使用统一基础节点和语义卡片模型 |
| HTML与JSON不一致 | JSON作为唯一权威源 |
| 主题污染内容 | 主题仅保存引用和Token |

| SVG执行风险 | 模板化生成＋禁止脚本 |

| 组件升级破坏旧文 | 组件版本并存 |
| 长文卡顿 | Node View按需加载与资源懒加载 |

# 四十一、技术决策冻结

本文件正式冻结以下技术决策：

1. 编辑器采用Tiptap，底层文档模型采用ProseMirror；
2. 编辑器内容以JSON为唯一权威数据；
3. HTML只用于导入、预览、复制、同步和导出；
4. 所有区块必须符合受控Schema；
5. 静态组件与SVG均为自定义Node；
6. 专业组件采用“语义＋Slot＋视觉变体”模型；
7. 主题Token与公众号品牌Token独立；
8. 样式局部覆盖使用受控JSON，不保存任意CSS；
9. 原文锁定由事务拦截和哈希校验共同实现；
10. 所有大型操作使用事务分组和版本快照；
11. 自动保存采用IndexedDB本地草稿＋服务端保存＋历史快照；
12. 微信HTML由服务端渲染器统一生成；
13. SVG禁止任意脚本，必须提供静态降级；
14. 第一版不启用实时协同，但预留Yjs接口；
15. 组件、主题和文档Schema均必须支持版本迁移。
